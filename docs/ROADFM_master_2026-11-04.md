### 1-1. 무엇을 해결하는가

1. 목적지로 이동하는 도중에 주변 지역의 역사·문화·장소를 알기 어렵고, 별도 검색은 번거롭다.
2. 내비게이션 경로는 주로 거리·시간 위주여서 **내 취향에 맞는 곳을 경유할 기회**를 충분히 알려주지 못한다.
3. 여행 뒤에 어디를 들렀고 어떤 이야기를 들었는지 기록하려면 수동으로 정리해야 한다.

**핵심 제안:** 이동을 단순한 대기 시간이 아닌 **오디오 청취 → 장소 발견 → 실제 체류 → 여행 기록**의 연속된 경험으로 만든다. 그 중심은 **듣는 경험**이며, 발견·기록은 청취를 이어 주는 주차 중 기능이다.

### 1-2. 서비스 우선순위

- **P0 / 핵심:** 위치·목적지와 연동한 검증된 **오디오 여행 채널**(Media3 기반 재생, 차량 미디어 화면·핸들 버튼·음성 검색 대응).
- **P1 / 청취 연계:** 주차 중 경로별 관광지 탐색 및 개인화 추천, 방문 추정 기록, 주행 중 들은 추천의 "나중에 보기".
- **P2 / 고도화:** 주차 중 퀴즈, 스탬프, Gleo 음성 기능 확장, 추천 개인화 향상.
- **향후:** 모바일 앱에서 취향·여행 기록 확인. **모바일 앱은 공모전 필수 산출물이 아니다.**

### 1-3. 설계 원칙: 주행 중엔 귀로, 주차 중엔 눈으로

Pleos 주행 규제상 DO(Distraction Optimized) 미선언 앱은 **주행(Drive) 중 사용 불가**이고, Music/Audio 카테고리의 주행 중 허용 범위는 앨범아트 등 단순 시각 정보와 재생·일시정지·넘기기 같은 단순 조작이다. 이를 제약이 아닌 설계 원칙으로 삼는다.

| 상태 | 사용자가 하는 일 | 담당 |
|---|---|---|
| **주행 중** (신호 대기 등 D단 정차 포함) | 이야기 듣기·멈추기·넘기기, 음성으로 "강릉 이야기 틀어줘" | 차량 미디어 화면(미디어 센터), 핸들 버튼, Gleo 음성 |
| **주차(P) 중** | 경로·장소 탐색, 나중에 보기 확인, 퀴즈, 여행 기록, 설정 | ROADFM 앱 화면 |

## 2. 브랜드·네이밍·디자인 방향

### ROADFM의 의미

- **Road:** 도로·여정·차량 이동.
- **FM:** 라디오처럼 위치에 맞는 지역 이야기 채널을 듣는 경험.
- 한글 발음: **로디엠**. 발음과 영문 철자 `ROADFM`이 완전히 일치하지 않으므로 브랜드 표기를 일관되게 유지한다.
- 과거 설명의 **BGM**은 음악 스트리밍으로 오인될 수 있어, 최종 메시지는 **FM/오디오 여행 가이드** 중심으로 정리한다.
- `ROADFM`은 기존 서비스·상표와 유사할 가능성이 있어 **최종 명칭 확정 전 KIPRIS 및 앱스토어 검색이 필요**하다. `RODIEM` 등의 표기는 후보이지 확정안이 아니다.

### 디자인 원칙

- **현대 모터스튜디오에 어울리는 예술적·감각적 분위기**: 절제된 타이포그래피, 넓은 여백, 풍경 중심의 감성.
- **실제 자동차 앱 같은 UI**: 읽기 쉬운 라벨, 기능이 보이는 컨트롤, 복잡한 AI 그래픽·과장된 글로우 배제.
- 다크 그린·차콜·아이보리 등 차분한 색과 제한적인 강조색 사용(차량 UI 가이드 우선).
- `NOW PLAYING`, 지역명, 재생 시간, 콘텐츠 제목처럼 **라디오/오디오 서비스의 실제 정보 구조**를 반영.
- `안내시작`보다 `여행 이야기 듣기`, `이야기 재생` 등 **내비게이션 자체로 오인되지 않는 버튼명**을 사용.
- ROADFM 화면에는 **목적지 검색 입력창·턴바이턴 안내·경로 안내 지도를 두지 않는다.** 목적지는 "내비 목적지: 강릉(현대차 내비에서 받아옴)"처럼 표시하고, 경로 비교는 "어떤 길의 이야기를 들을까요?"처럼 이야기 선택으로 표현하며 소요 시간은 `예상`으로 표기한다.
- **주행 시**: 차량 미디어 화면에 지역 아트워크·이야기 제목·지역명·진행 정보만. 지도·소리 물결 등 움직이는 그래픽 없음. **주차(P) 시**: 경로 비교·장소 상세·퀴즈·기록 편집.

## 3. 사용자 시나리오와 서비스 흐름

### 대표 시나리오: 서울 → 강릉 자동차 여행

**🅿️ 출발 전 (주차 중)**

1. 사용자가 차량 내비게이션에서 **강릉**을 목적지로 설정한다.
2. ROADFM은 **NaviHelper**를 통해 가능한 범위에서 목적지·경로 안내 상태를 확인하고, **"강릉 가는 길" 이야기 목록**을 준비한다.
3. (선택) 사용자가 ROADFM 화면에서 취향(자연·카페·역사 등)과 **경로 인근에 들르기 좋은 장소**를 살펴보고 관심 장소를 저장한다.
4. 사용자가 **"이야기 듣기"**를 누른다. 핸들 버튼이나 음성("강릉 가는 길 이야기 틀어줘")으로도 시작할 수 있다. **사용자가 시작하기 전에는 재생하지 않는다.**

**🚗 주행 중 (귀로)**

5. 이야기는 **차량 미디어 화면**(지역 아트워크·제목·진행)과 핸들 버튼·Tune Knob·음성으로 조작한다. ROADFM 자체 화면은 열리지 않는다.
6. "이어서 듣기"를 켠 경우, 한 이야기가 끝나면 **현재 위치에 맞는 다음 지역 이야기**가 재생 목록에 이어진다. 사용자가 멈추거나 끈 뒤에는 위치가 바뀌어도 다시 시작하지 않는다.
7. 이야기 중 "20분 뒤 지나는 ○○에 들를 만한 곳이 있어요" 같은 **오디오 안내**가 나오면, 사용자는 들은 장소를 **"나중에 보기"**에 담는다(음성 저장은 Pleos 확인 후).
8. 내비 안내·통화·음성비서가 나오면 이야기는 잠시 멈췄다가 이어진다.

**🅿️ 도착·휴식 (주차 중, 눈으로)**

9. 휴게소나 관광지에 주차하면 "나중에 보기"에 담긴 장소의 상세 정보를 확인한다.
10. 사용자가 **자동 기록에 사전 동의**했다면, 추천 장소에 일정 시간 체류했을 때 **방문 추정**으로 여행 기록에 남긴다. 이후 수정·삭제할 수 있다.
11. 들은 이야기를 바탕으로 한 **퀴즈·스탬프·여행 기록**을 확인한다.

### 기능 흐름

```text

[차량 내비 목적지 설정] → [NaviHelper 목적지/상태 조회]
          │
          ├──────────────────────────────┐
          ▼                              ▼
```

## 4. 기능별 요구사항

### F-01. 차량 내비 목적지 연동 — P0

- **ROADFM은 길 안내를 하지 않는다.** 목적지 설정과 길 안내는 현대차 기본 내비가 하고, ROADFM은 NaviHelper로 결과를 받아 쓴다. 앱 안에 목적지 검색 UI를 두지 않는다.
- 내비에 목적지가 없으면 "내비에서 목적지를 설정해 주세요"로 안내하고, 목적지 없이도 현재 위치 기반 추천 이야기는 들을 수 있게 한다.
- 목적지·내비게이션 안내 상태 조회. **목적지·경로는 "이 길의 이야기" 재생 목록을 구성하는 입력**으로 쓴다.
- SDK의 콜백으로 경로 변경/목적지 변경 등 반영(재생 목록 갱신, 재생 중인 이야기는 끊지 않음).
- 경유지 추가는 **주차(P) 상태에서 사용자의 명시적 선택**으로만 요청. 주행 중 음성 경유지 추가는 Pleos 카테고리 정책 확인 후 검토.
- 결과/실패/권한 문제/SDK 미지원 상태를 UI로 구분.

### F-02. 오디오 여행 채널 (관광 오디오 가이드) — P0

**콘텐츠**

- 위치 및 목적지와 관련된 **검증된 관광정보** 조회.
- LLM은 관광정보를 바탕으로 **짧은 청취용 대본**과 제목을 생성.
- 정제·검증된 대본은 사전에 TTS로 오디오 파일로 만들어 캐시하는 방식을 우선 검토.
- 이야기마다 재생성되어도 바뀌지 않는 **고정 ID(`storyId`)**를 부여한다(미디어 ID 기반 재생 요건).

**재생 구조 (Pleos Music/Audio 가이드 필수 요건)**

- Media3 `MediaLibraryService` + ExoPlayer로 구현하고, 레거시 `MediaBrowserService` 인터페이스도 함께 노출한다.
- 브라우즈 트리는 단일 혼합 리스트가 아니라 **[이 길의 이야기] [지역별] [주제별] [최근 들은 이야기]**로 나눈다.
- 주행 중 재생 화면은 **미디어 센터(차량 미디어 화면)**에 맡기고 지역 아트워크·제목·지역명·길이 메타데이터를 채운다.
- 핸들 버튼 최소 지원: 재생, 일시정지, 정지, **미디어 ID 기반 재생**, **검색 기반 재생**, 이전/다음.
- Gleo 음성: `MediaLibraryService` 검색 구현으로 "○○ 이야기 틀어줘"에 대응(1단계). Gleo Interface로 ROADFM 전용 음성 기능 3~5개 추가(2단계, P2).

**재생 규칙**

- **자동 재생 금지:** 시동·연결·프로필 변경 시 재생하지 않는다. 재생은 사용자의 명시적 동작(화면·핸들 버튼·음성) 또는 시스템 재개 요청으로만 시작한다.
- 재생 상태를 `IDLE` / `PLAYING` / `PAUSED_BY_USER` / `PAUSED_BY_FOCUS`로 관리한다.
- **"이어서 듣기"(기본 OFF):** `PLAYING`일 때만 위치 기반 다음 이야기를 큐 뒤에 추가한다. `IDLE`·`PAUSED_BY_USER`에서는 위치가 바뀌어도 재생을 시작하지 않는다.
- 같은 콘텐츠 중복 재생을 방지하고, 새 관광지가 감지돼도 재생 중인 이야기를 끊지 않는다.

**오디오 포커스·생명주기**

| 이벤트 | 처리 |
|---|---|
| `AUDIOFOCUS_LOSS` | 정지 → `IDLE`. 세션을 active로 남기지 않고 자동 재개하지 않음 |
| `AUDIOFOCUS_LOSS_TRANSIENT` (통화, Gleo 호출) | 일시정지 → `PAUSED_BY_FOCUS`, `GAIN` 시에만 재개 |
| `AUDIOFOCUS_LOSS_TRANSIENT_CAN_DUCK` (내비 안내) | 말소리 콘텐츠이므로 **일시정지 + 3초 되감기** 제안. Pleos 권장은 볼륨 감쇄 → 확인 후 확정 |
| 앱 스와이프 종료 / 쓰리핑거 | 재생 정지 → `stopSelf()` (Pleos 가이드의 `onTaskRemoved` 순서 준수) |

- `AudioAttributes`는 `USAGE_MEDIA` + `CONTENT_TYPE_SPEECH`. 내비 안내용 usage를 쓰지 않는다.
- GPS가 부정확하거나 네트워크가 끊기면 안전한 기본 동작(오프라인 캐시/재생 보류).

### F-03. 경로별 맞춤 장소 추천 — P1 (주차 중)

- 출발지·목적지 기준 **경로 후보** 확보. 이 경로 후보는 길 안내용이 아니라 **이야기·장소 추천을 위한 예상 경로**이며, 화면에서도 "예상"으로 표기한다.
- 각 경로의 도로 좌표 주변 관광지 후보를 찾는다.
- **경로 직선거리뿐 아니라 실제 경유 시 늘어나는 소요 시간**을 평가한다.
- 사용자가 `자연·풍경 / 카페·미식 / 역사·문화` 등 취향을 선택한다.
- 경로·취향을 바꾸면 추천 결과가 변경된다.
- 관광지 선택 후 상세정보 및 경유지 추가 요청(플랫폼 지원 범위 내) 가능.
- **경로 후보는 실제 내비 경로와 다를 수 있음**을 내부적으로 관리한다.
- **기본은 "내비 경로 그대로"**: 현대차 내비 경로(또는 이를 근사한 예상 경로) 기준으로 들를 곳을 추천한다. ROADFM에서 다른 길을 고르는 것만으로는 내비 경로가 바뀌지 않는다.
- **다른 길 제안(선택)**: "풍경 좋은 길로 가 볼까요? 예상 +24분 · 양평 두물머리 경유"처럼 제안하고, 사용자가 수락하면 **내비에 경유지 추가를 요청**해 경로를 바꾼다. "원래 내비 경로로" 되돌리기도 제공한다.
- **내비 경유지는 최대 2개**(NaviHelper `WaypointIndex.FIRST/SECOND`). 다른 길 제안도 경유지 1칸을 쓴다. 여정 탐색에 "내비 경유지 n/2"를 표시하고, 가득 찼을 때 추가하면 "어느 경유지를 뺄까요?"로 바꿀 곳을 고르게 한다. 실제 구현에서는 추가 전에 `getWaypointInfo()`로 사용자가 내비에서 직접 넣은 경유지까지 포함해 남은 칸을 확인한다.
- 취향은 **첫 실행 때 한 번**(복수 선택, 건너뛰면 골고루) 고르고 설정에서 바꾼다. 여정 탐색에는 "취향 · 자연·풍경, 역사·문화 · 바꾸기"처럼 작게 표시한다. 취향은 들를 곳 추천과 다른 길 제안 모두에 반영한다.
- 추천 화면·장소 상세는 **주차(P) 상태에서만** 사용한다.
- **주행 중에는 화면 대신 오디오로 안내**한다(예: "20분 뒤 지나는 ○○에 들를 만한 곳이 있어요"). 사용자는 **"나중에 보기"**에 담고 다음 주차 때 확인한다.

### F-04. 체류 기반 방문 추정·자동 기록 — P1

- 사용자가 자동 기록을 **명시적으로 켠 경우**에만 동작.
- 재생 서비스와 **분리된 컴포넌트**로 구현하고, 여정이 진행 중일 때만 동작한다(앱 종료 시 재생 서비스는 정지해야 하므로).
- 위치 정확도, 관광지 거리, 이동 속도, 체류 시간, 중복 방문을 함께 확인.
- **초기 검증용 가정:** 150m 이내 + 위치 오차 50m 이하 + 3km/h 이하 + 10분 체류.
- 위 수치는 **확정 정책이 아니라 테스트용 임계치**이며 장소 특성/실측 데이터로 보정 필요.
- `방문 추정`과 `사용자 확인 방문`을 구분.
- 단순 통과·도로 정체·GPS 흔들림·장소 앞 카페 체류를 방문 확정으로 표시하지 않는다.
- GPS가 불안정하면 체류 누적을 보류.
- 동일 여정/장소 중복 방지. 기록 확인·수정·삭제 기능 제공.

### F-05. 퀴즈·스탬프 — P2 (주차 중)

- 참여형 퀴즈는 **주차(P) 상태에서만** 제공한다. 동승자 예외는 Pleos 문서상 근거가 없어 두지 않는다(확인되면 재검토).
- 주행 중에는 이야기 끝에 **응답을 요구하지 않는 "생각해 볼 질문"**만 오디오로 던지고, 정답·해설은 주차 후 확인한다(게임 유도에 해당하지 않는지 Pleos 확인).
- 퀴즈는 검증된 설명 데이터에 기반해 생성하고 출처/정답/해설을 보유.
- 시간 제한·과도한 애니메이션·주행 중 응답 강요 금지.
- 방문 기록/이야기 청취를 바탕으로 스탬프 제공(단순 통과와 실제 체류 구분).

### F-06. 모바일 확장 — 이후

- 모바일은 **필수 개발 대상이 아님**. 차량용 Pleos 앱 우선.
- 모바일에서 취향 설정, 여행 기록 보기, 저장 장소 관리 가능하도록 설계하되, 초기 제출은 기획에만 반영.
- 차량 ↔ 모바일 연동은 사용자 계정 및 **ROADFM 자체 백엔드**가 담당한다. Pleos가 자동 동기화해 준다고 가정하지 않는다.

### 6-2. 권장 스택

| 영역 | 권장 기술 | 설명 |
|---|---|---|
| 차량 앱 | Kotlin + Android / 필요 시 Jetpack Compose | Pleos SDK 연동과 차량용 UI |
| 차량 플랫폼 | Pleos Connect Emulator | 실제 차량용 앱 환경 테스트 |
| 차량 내비 | NaviHelper SDK | 목적지/경로 안내·경유지 제어 |
| 위치 | NaviHelper가 제공하는 위치 정보부터 검증 | FusedLocation은 SDK 사용 상태 확인 후 적용 |
| 차량 상태 | Vehicle State SDK(필요 시) | 지원 항목 범위 내 사용 |
| 오디오 | Media3 `MediaLibraryService` + ExoPlayer + Audio Focus | Pleos Music/Audio 가이드 필수 요건(MBS·MediaSession·검색) 충족 |
| 주행 중 UI | Pleos 미디어 센터(차량 미디어 화면) | 핸들 키·Tune Knob·Media 버튼·미디어 앱 라이브러리 연동. 연동 API는 문서 확보 후 |

| API 서버 | Spring Boot (Java 21 검토) | 프런트와 외부 API 연결, 인증/추천 처리 |
| 데이터베이스 | PostgreSQL + PostGIS | 관광지·경로 공간 검색 |
| 관광정보 | 한국관광공사 TourAPI | 관광지·음식점·문화 등 공식 데이터 |
| 역사정보 | 국가유산 관련 공공 API(선택) | 문화재 설명 검증 강화 |
| 도로 경로 | 외부 자동차 길찾기 API(예: 카카오모빌리티) | 대안 경로 및 좌표 확보 가능 여부 검증 |
| LLM | 별도 서버에서 호출하는 외부 모델 | 설명 요약, 퀴즈, 추천 문구 |
| 음성 합성 | 사전 생성한 TTS 음원 + 캐시 | Pleos TTS 사용이 제한된 상황의 대안 |

### 6-3. Pleos SDK 사용 가능성 — **특히 중요**

2026-11-04 기준 공식 프로젝트 생성/SDK 신청 문서에 표시된 상태:

| 항목 | 문서상 상태 | 개발 판단 |
|---|---|---|
| **NaviHelper** | **사용 가능** | **최우선 실연동** |
| **Vehicle State** | **사용 가능** | 필요한 경우 활용 |
| **FusedLocation** | 준비 중 | 사용 권한/실구동 확인 전까지 의존 금지 |
| **TextToSpeech** | 준비 중 | 안드로이드 미디어 플레이어 + 외부 음원 대안 |

- 공식 문서에 API 설명이 보이는 것과 **개발자 프로젝트에서 실제 사용 가능한 것**은 다르다.
- SDK 상태·에뮬레이터 버전은 변경될 수 있으므로 구현 시작 시 재확인한다.
- 공식 참고: <https://document.pleos.ai/docs/pleos-only/create-my-project>

### 6-4. 내비게이션 연동: 확인된 부분과 미확인 부분

**확인된 NaviHelper 범위:** 목적지 확인·설정, 경로 옵션 변경/재탐색, 경유지 추가·제거, 경로 안내 상태·이벤트 등.

**공식 문서 재확인 (2026-11-12, NaviHelper SDK v3.0.5 가이드 기준):**

- 목적지 조회: `getDestinationInfo()` → 결과는 `NaviHelperEventListener.onDestinationInfo(destinationInfo: DestinationInfo)` 콜백으로 수신(직접 반환 없음).
- 목적지 변경 이벤트: `onDestinationChanged()` — "목적지가 설정되거나 제거될 때" 호출. 그 밖에 `onRouteStarted(routeStartInfo)`, `onRoutingCompleted()`, `onRouteCancelled()`, `onReRouteEnded()`, `onDestinationArrived()`, `onWaypointChanged()`, `onCurrentLocationInfo()`, `onRouteStateInfo()`, `onTBTInfo()`, `onTripInfo()` 등 25개 콜백 존재.
- 경로 옵션(`RouteOption`): `RECOMMENDED`, `SHORT_DISTANCE`, `SHORT_TIME`, `FREE`, `HIGHWAY`, `COMFORTABLE`, `SCHOOL_ZONE` — "풍경 좋은 길" 같은 옵션은 없으므로 다른 길은 **경유지 추가**로 유도한다.
- 경유지: `addWaypoint(RequestWaypointInfo)`(위도·경도·poiName·poiId·address·`WaypointIndex`), `getWaypointInfo()` → `onWaypointInfo(List<WaypointInfo>)`, `removeWaypoint(WaypointIndex.FIRST|SECOND|ALL)`. **경유지는 최대 2개.** 목적지+경유지를 한 번에 요청하는 `requestRouteWithWaypoints(RouteWithWaypointsRequest)`도 있으며 `pleos.car.permission.NAVI_ROUTE_SEARCH` 권한 필요. 경유지 추가 시 자동 재탐색 여부·사용자 확인 팝업·활성 경로 필요 여부는 문서에 없음.
- **문서로 확인 안 됨:** ① 사용자가 내비 앱에서 직접 설정한 목적지도 `getDestinationInfo()`/`onDestinationChanged()`로 오는지(문서: "Navigation 앱의 구현 시나리오에 따라 전달되는 이벤트가 달라질 수 있음"), ② ~~`DestinationInfo` 필드~~ → SDK AAR(3.0.5 / navi-data 3.0.4) 공개 API로 확인: `name`, `address`, `latitude`, `longitude`, `displayLatitude`, `displayLongitude`, `remainDistance`, `remainTime`, `tollFare`, `poiId`, `poiSubId`, `poiProvider`. 리스너 메서드는 모두 default라 필요한 것만 구현하면 됨(경유지 조회 콜백 실제 이름은 `onWayPointInfo`). 확인용 화면: `apps/vehicle` `NaviProbe`, ③ 경로 좌표(polyline)·대안 경로 제공 여부.
- **검증 방법:** 에뮬레이터 내비에서 사용자가 직접 목적지 설정 → ROADFM에서 `getDestinationInfo()` 호출 및 `onDestinationChanged()` 수신 로그 확인. 안 되면 현재 위치 기반 이야기로 동작하고 Pleos에 문의.

**확인되지 않은 요구사항:**

- 기본 내비의 모든 대안 경로를 앱으로 열거할 수 있는지.
- 사용자가 기본 내비 화면의 **특정 경로 카드를 탭한 이벤트**를 외부 앱이 받는지.
- 선택된 **전체 도로 경로 Polyline**을 그대로 반환받을 수 있는지.

**현실적 우회안:**

1. NaviHelper에서 **현재 목적지 + 안내 상태**를 가져온다.
2. ROADFM 서버가 외부 길찾기 API로 **자체 경로 후보**를 계산한다.
3. 외부 경로별 관광지 후보를 분석해 ROADFM 화면에서 선택/추천한다.
4. 추천 장소의 경유지 추가는 SDK 범위 내에서 사용자가 명시적으로 요청한다.
5. 내비가 경로를 재탐색하거나 실제 차량이 예상 경로를 벗어나면 콘텐츠 후보를 갱신한다.
6. **외부 예상 경로 ≠ 실제 기본 내비 경로**일 수 있음을 데이터 모델과 시연 설명에 명시한다.

초기 제출용 MVP는 **목적지 기반 콘텐츠 + 현재 위치 기반 주변 관광지**부터 구현하는 편이 기술 위험이 낮다.

### 6-5. 경로별 관광지 추천 알고리즘

```text
출발지/목적지 → 외부 경로 후보(Polyline) → 경로 버퍼 공간 검색(PostGIS)
→ 관광지 후보 → 실제 도로 우회 시간 산정 → 취향 적합도 가중치
→ 운영 상태/중복/콘텐츠 적합성 필터 → 최종 추천
```

**초기 추천 규칙 예시(정책 확정 아님):**

- 경로 주변 2km 내 관광지를 1차 검색.
- **추가 우회 시간 15분 이내**를 우선 추천.
- 자연·풍경/카페·미식/역사·문화 등 관심사를 가중치로 사용.
- 현재 영업 여부·접근성·데이터 신뢰도 고려.
- 이미 방문한 곳은 후순위로 조정 가능.

PostGIS 예: `ST_DWithin(road_geometry, place_geometry, radius)`로 공간 후보 선정. **실제 진입 경로와 우회 소요 시간은 별도 경로 API로 검증**해야 한다.

### 6-6. 방문 판정 로직 (옵트인 전제)

```text
사용자가 '방문 자동 기록' 활성화
    ↓
관광지 지오펜스 진입
    ↓
GPS 정확도 만족? ── 아니오 → 기록 판단 보류
    ↓ 예
저속/정차 상태 지속?
    ↓ 예
10분 체류 조건 만족? ── 아니오 → 후보 유지
    ↓ 예
동일 장소/동일 여행 중복 체크
    ↓
'방문 추정' 저장 → 사용자가 확인/수정/삭제 가능
```

**주의:** 시연의 '현장 도착 → +5분 체류'는 버튼을 통한 가상 시간 진행일 뿐, 실제 차량 위치 추적 결과가 아니다.

### 6-7. AI 활용 원칙

- LLM은 **검증된 사실을 전달하는 콘텐츠 작가/요약기** 역할.
- 관광정보 API의 사실과 출처를 먼저 저장하고, 대본·퀴즈가 이를 벗어나지 않도록 제한.
- **AI가 실제 추천 경로·관광지·영업 상태를 임의로 지어내지 않도록** 경로/장소 계산은 결정적인 데이터 처리로 수행.
- 생성 결과는 `sourceId`, `sourceText`, `generatedAt`, `modelVersion`, `verificationStatus` 등으로 추적.
- API 비밀키는 서버에 보관. APK에 삽입하지 않는다.
- 모든 오디오를 실시간 생성하지 않고 **자주 쓰는 콘텐츠 사전 생성·캐시**.
- 정확한 퀴즈 정답 및 근거가 없는 경우 출제하지 않는다.

## 8. 차량 안전·개인정보·운영 요구사항

### 주행 안전

1. ROADFM 앱 화면은 **DO 미선언** → 주행(Drive) 중 시스템이 차단. 주행 중 조작은 **미디어 센터·핸들 버튼·Gleo 음성**으로만 한다. 주행용 자체 화면이 필요해지면 해당 Activity만 DO 선언 + `CarUxRestrictions` 연동(선언 방식 Pleos 확인).
2. 상세 경로 비교, 장소 탐색, 퀴즈, 기록 편집, 설정은 **주차(P) 상태 전용**. 신호 대기 등 D단 정차는 주행으로 간주한다.
3. 내비·안전·통화·음성비서 오디오가 ROADFM보다 우선. **Audio Focus** 처리는 F-02 표를 따른다.
4. 시동·연결·프로필 변경 시 자동 재생 금지. 사용자가 멈추거나 끈 뒤에는 자동 재시작 금지.
5. 주행 중 화면(차량 미디어 화면)에는 정적 아트워크·제목·지역명·진행만 표시. 지도·애니메이션·긴 글 없음.
6. 앱 카테고리는 **Music/Audio**로 확정하고, 비오디오 기능은 "청취 연계 주차 기능"으로 설명한다. 심사 수용 여부는 Pleos에 확인(12장).

### 개인정보

1. **위치기반 서비스의 필수 위치 사용**과 **방문 기록 보존 동의**는 별개로 설명.
2. 모든 이동 궤적을 상시 저장하지 말고 관광지 조회에 필요한 최소 위치만 전송.
3. 추정 방문은 사용자가 수정·삭제할 수 있게 제공.
4. 회원 계정/모바일 동기화가 생기면 인증·권한·암호화·보존 정책을 추가.

### 견고성

- 경로 변경 시 기존 콘텐츠 후보 무효화 및 재조회.
- 오디오 재생 중 새로운 관광지가 감지돼도 즉시 끊지 않고 큐 조정.
- 관광지 반경에서 GPS가 흔들릴 때 중복 실행 방지.
- 통신 불량 시 캐시된 콘텐츠만 재생하거나 기능 보류.
- 관광정보 API 응답 누락·폐업·데이터 오류 처리.
- 외부 지도 API 예상 경로와 실제 주행 경로 불일치 감지.

## 11. 공모전 제출용 설명 문구 초안

### 서비스 개요

> **ROADFM(로디엠)**은 Pleos Connect 차량 환경에서 목적지·이동 위치에 맞춰 지역의 역사·문화·관광 이야기를 들려주는 **위치 기반 오디오 여행 채널**입니다. 검증된 관광 데이터로 만든 짧은 이야기를 차량 미디어 화면·핸들 버튼·음성으로 듣고, 주차 중에는 들은 이야기에서 이어지는 경로 위 장소 발견과 여행 기록을 제공합니다. 이용자가 동의한 경우, 위치 및 체류 상태를 바탕으로 방문을 추정해 여행 기록으로 이어 줍니다.

### 차량에서만 더 가치 있는 이유

> ROADFM의 설계 원칙은 **"주행 중엔 귀로, 주차 중엔 눈으로"**입니다. 주행 중에는 화면을 쓰지 않고 차량 미디어 화면·핸들 버튼·음성 비서만으로 이야기를 듣고, 내비 안내·통화가 나오면 오디오 포커스 정책에 따라 양보합니다. 경로 비교·장소 상세·퀴즈·기록은 주차 상태에서만 제공합니다. 스마트폰에서 관광 정보를 검색하는 방식과 달리, 목적지·위치라는 이동 맥락 자체가 이야기의 재생 목록이 됩니다.

### 기술 구현 계획

> Kotlin 기반 Pleos 차량용 앱은 Media3 `MediaLibraryService`로 이야기 재생·탐색·검색을 제공해 차량 미디어 화면, 스티어링 휠 키, Gleo 음성 명령과 연동하고, NaviHelper SDK로 목적지와 내비게이션 안내 상태를 받아 "이 길의 이야기" 목록을 구성합니다. Spring Boot 백엔드는 한국관광공사 관광정보와 경로 탐색 데이터를 결합해 경로 주변 관광지를 선별·추천합니다. AI는 검증된 사실을 활용한 오디오 대본·퀴즈 생성에 한정하고 음원은 사전 생성·캐시합니다. 위치 SDK의 가용성은 검증 후 방문 판정 기능에 단계적으로 연결합니다.

### 핵심 차별화

> **지나가는 길을 듣고, 들은 이야기에서 들를 곳을 발견하고, 머물렀던 순간을 기록한다.** ROADFM은 듣는 경험을 중심으로 분절된 검색·관광 안내·기록 단계를 하나의 차량 여행 흐름으로 연결합니다.

### 기대 효과 (검증 목표)

- 이동 중 관광정보 검색 부담 완화.
- 경로 주변 숨은 관광지 인지와 자발적 방문 확대.
- 음성 중심의 안전한 여행 경험.
- 여행 기록에 기반한 재사용 및 콘텐츠 개인화 가능성.

> **주의:** 실제 이용률, 관광지 유입 증가, 재방문율 개선은 아직 측정한 성과가 아닌 **기대 효과와 추후 검증할 가설**이다.

## 13. 경쟁 서비스·시장성 논리

**벤치마크 후보:** Autio, GuideAlong, VoiceMap. 이들처럼 위치 기반 오디오 가이드라는 접근은 이미 존재하므로, 단순히 `차량에서 지역 이야기를 들려준다`는 기능만으로 독창성을 주장하지 않는다.

ROADFM이 강조할 지점은 다음과 같다.

1. **차량 네이티브 청취:** 차량 미디어 화면·핸들 버튼·Gleo 음성·오디오 포커스와 연결된, 운전 중 화면을 보지 않는 오디오 경험.
2. **경로가 곧 재생 목록:** 내비 목적지·경로로 "이 길의 이야기"를 구성하고, 들은 이야기에서 들를 곳으로 이어 준다.
3. **개인화:** 사용자의 관심사와 허용 우회 시간에 맞는 장소를 추천한다(주차 중).
4. **여정 축적:** 자동으로 추정된 방문을 사용자가 선택적으로 여행 기록으로 남긴다.

**기획서 시장자료 후보(제출 전 반드시 원문 대조):**

- 한국관광공사 2026 관광 트렌드 (AI 여행 조력자·로컬 경험): <https://academy.visitkorea.or.kr/macademy/notice/bbs/detail.do?seq=3512>
- 한국관광공사 관광정보 공공 API: <https://www.data.go.kr/data/15101578/openapi.do>
- NHTSA 주의 분산 관련 자료: <https://www.nhtsa.gov/sites/nhtsa.gov/files/distraction_npfg-02162012.pdf>
- 여행 기록/관광 동향 수치: 기존 작성 기획안에 출처 후보가 있으나, **숫자 자체는 이 문서에서 사실로 확정하지 않음.**

**사업성 KPI(예시, 목표치 미확정):** 오디오 청취 시작률, 오디오 완료율, 추천 장소 열람률, 관심 장소 저장률, 방문 추정/확인 비율, 여행 후 기록 재열람률, 30일 재이용률. 기획안에는 측정 방법과 가설을 우선 제시한다.
